# 部署模式（组件架构）

### 1. 单机模式 (Standalone)

最基础的部署方式，只有一个 Redis 实例。

- **特点：** 部署极其简单，直接安装运行即可。
- **优点：** 架构简单，没有一致性问题，配置方便。
- **缺点：**
  - **无高可用：** 实例宕机则服务完全不可用。
  - **性能上限：** 受单机 CPU、内存和网卡带宽限制。
- **适用场景：** 开发测试、对可用性要求极低的小型工具类应用、本地缓存。

------

### 2. 主从复制模式 (Master-Slave / Replication)

通过 `replicaof` 命令让一个主节点（Master）拥有多个从节点（Slave）。

- **原理：**
  - **读写分离：** 主节点负责写操作，并将数据异步同步给从节点；从节点负责读操作。
  - **数据备份：** 从节点是主节点的实时数据副本。
- **优点：** 极大提升了系统的读吞吐量；实现了数据冗余。
- **缺点：**
  - **无法自动故障切换：** 主节点挂了后，需要人工干预（手动把一个从节点升为主节点并修改客户端配置）。
  - **容量限制：** 所有节点存储的数据量完全一致，受限于单机内存。
- **适用场景：** 读多写少的简单高可用场景。

------

### 3. 哨兵模式 (Sentinel)

在主从模式的基础上引入了“哨兵”集群，实现了**自动化的故障发现与转移**。

- **原理：** 哨兵是一个独立的进程，负责监控所有 Redis 节点。当发现主节点下线时，通过选举协议（Quorum）自动选出一个从节点升级为新主。
- **优点：**
  - **高可用：** 真正实现了 7×24 小时无人值守的自动化运维。
  - **客户端透明：** 客户端通过哨兵获取当前主节点地址，主从切换对业务透明。
- **缺点：**
  - **资源浪费：** 依然受限于单机内存容量。
  - **架构复杂：** 需要额外部署并维护哨兵集群（通常至少 3 个节点）。
- **适用场景：** 对可用性要求极高的中小型数据量业务。

------

### 4. 集群模式 (Redis Cluster)

Redis 3.0 推出的真正**分布式**解决方案。

- **原理：** 采用分片（Sharding）机制。集群将数据分为 **16384 个哈希槽（Slots）**，均匀分布在不同的主节点上。每个主节点通常配有至少一个从节点。
- **特点：**
  - **去中心化：** 节点之间通过 Gossip 协议交换状态，没有中心控制节点。
  - **横向扩展：** 可以通过增加节点轻松扩展到上千台服务器，突破单机内存瓶颈。
  - **高可用：** 集群内部自带故障检测和自动切换功能，无需额外哨兵。
- **缺点：**
  - **批量操作受限：** 跨槽（Cross-slot）的多键操作（如 MSET）受到限制。
  - **事务减弱：** 仅支持同一哈希槽内的事务。
- **适用场景：** 大规模生产环境、海量数据存储、超高并发写需求。



| **特性**         | **单机模式** | **主从模式**   | **哨兵模式**          | **集群模式**         |
| ---------------- | ------------ | -------------- | --------------------- | -------------------- |
| **高可用**       | 否           | 需人工干预     | 是（自动切换）        | 是（自动切换）       |
| **数据冗余**     | 否           | 是             | 是                    | 是                   |
| **横向扩展**     | 不支持       | 仅限读扩展     | 仅限读扩展            | **支持读写扩展**     |
| **客户端复杂性** | 低           | 中             | 中（需支持 Sentinel） | 高（需支持 Cluster） |
| **数据一致性**   | 强（单机）   | 弱（异步同步） | 弱（异步同步）        | 弱（异步同步）       |
