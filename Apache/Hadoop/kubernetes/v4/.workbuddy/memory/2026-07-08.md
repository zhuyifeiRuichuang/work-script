## YARN HA Closure — NM Fixes Verified On-Disk + Two User Errors Diagnosed
- **NM yaml fixes already on disk (re-verified by reading files)**:
  - `nodemanager.yaml`: 3 probes (liveness/readiness/startup) changed `httpGet:/ws/v1/nodeinfo:8042` → `tcpSocket:8042`. Root cause of CrashLoop: Hadoop 3.1.1 REST endpoint returns 404 for `/ws/v1/nodeinfo` → kubelet Killing loop. tcpSocket passes once NM binds 8042.
  - initContainer `wait-for-resourcemanager` now gates on `nc -z resourcemanager-0.resourcemanager 8032 || nc -z resourcemanager-1.resourcemanager 8032` (HA-aware: either RM).
  - Main container: removed `echo "127.0.0.1 $(hostname)..." >> /etc/hosts`. That legacy line made Java reverse-resolve 127.0.0.1 → localhost, so NM registered as `localhost:<port>` and AMs couldn't route. Now relies on K8s-injected `<PodIP> <hostname>.<svc>` + `hosts: files dns` nsswitch → NM registers with FQDN.
- **Error 1 (pi job failed)**: `yarn jar $HADOOP_HOME/share/.../hadoop-mapreduce-examples-*.jar pi 2 1000` → `JAR does not exist: /share/hadoop/...`. Root cause: `$HADOOP_HOME` is NOT exported in a non-interactive `kubectl exec -- sh -c` shell (only set in login shells via hadoop-env.sh). Path collapses to empty. **Fix**: use absolute path `/opt/hadoop/share/hadoop/mapreduce/hadoop-mapreduce-examples-*.jar`.
- **Error 2 (failover no-op, twice)**: user deleted `resourcemanager-0` then `resourcemanager-1`, but BOTH times the deleted pod was the STANDBY (rm1/rm2 roles had flipped between attempts). Standby deletion does NOT trigger failover. **Fix**: always `yarn rmadmin -getServiceState rm1/rm2` FIRST, then `delete pod` of the ACTIVE RM. RM HA only proves itself when the active is killed.
- **closure runbook (user to execute, kubectl not in agent sandbox)**:
  1. `kubectl apply -f nodemanager.yaml && kubectl rollout restart statefulset/nodemanager -n hadoop1` → watch NM 3/3, restarts stop.
  2. `kubectl logs -n hadoop1 nodemanager-2 -c nodemanager --tail=20` → expect `Registered with ResourceManager as <fqdn>:<port>` (NOT `localhost`).
  3. `kubectl exec -n hadoop1 resourcemanager-0 -c resourcemanager -- yarn jar /opt/hadoop/share/hadoop/mapreduce/hadoop-mapreduce-examples-*.jar pi 2 1000` → expect ACCEPTED→RUNNING→`Estimated value of Pi is 3.14...`. (If stuck ACCEPTED → NM not 3/3.)
  4. Real failover: `getServiceState rm1/rm2` → `delete pod <ACTIVE>` → watch other RM go standby→active in ~10-30s; running job continues (ZKRMStateStore). For clean proof, run a longer job (e.g. `pi 10 1000`) and delete active while RUNNING.
