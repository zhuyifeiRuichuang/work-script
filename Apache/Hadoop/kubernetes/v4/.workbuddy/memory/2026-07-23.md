## namenode-1 CrashLoopBackOff 排障（核心）
- 现象：namenode-1 主 NN `NameNode is not formatted`，init 日志 `Access denied for user hadoop. Superuser privilege is required`。

## 统一根因（关键！）：容器 hostname → IPv6 link-local
- 症状组合：NN `local host is: (unknown)` 崩溃（Exit 6）+ ZK `not currently serving`（3 节点选不出 leader，`Cannot open channel to X:3888 Connection refused`，但 DNS 解析 peer 为 IPv4 正常）。
- 根因：容器内 `hostname` 经 nsswitch `myhostname` 模块**只解析到 IPv6 link-local (`fe80::...`)**。JVM/ZK 据此把端口（NN RPC、ZK 选举端口 3888）绑定到本机外不可达的 IPv6 地址 → peer 互连 3888 refused → ZK 无 quorum；NN `InetAddress.getLocalHost()` 返回 (unknown) → 崩溃。
- 修复（统一）：① JVM 级强制 IPv4 `-Djava.net.preferIPv4Stack=true`；② init 容器追加 `127.0.0.1 $(hostname)` 到 /etc/hosts（pod 级共享文件，主容器可见）。
- 应用位置：
  - `namenode.yaml`：init 加 /etc/hosts 兜底 + 主容器/ZKFC `HADOOP_OPTS=-Djava.net.preferIPv4Stack=true`（已改，待重建）。
  - `zookeeper.yaml`：新增 `init-hosts` init 容器（root 写 /etc/hosts）；JVM 选项注入**改用 `JAVA_TOOL_OPTIONS`**（见下）。
- **⚠️ 关键坑（实测 15:5x 轮次）**：`zookeeper:3.4.14` 镜像的 entrypoint **不读取 `ZOO_JAVA_OPTS`**！第一轮用 `ZOO_JAVA_OPTS=-Djava.net.preferIPv4Stack=true`，重建后 ZK 选举端口仍绑 IPv6 `::`（日志 `QuorumPeer[myid=1]/0:0:0:0:0:0:0:0:2181`），3 节点仍 `not currently serving`。**正确做法：用 `JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true`** —— 这是 JVM 启动器自身无条件 prepend 到所有 java 进程的环境变量，与镜像/启动脚本如何拼命令无关，跨版本最可靠。NN/Hadoop 侧 `HADOOP_OPTS` 同样补加 `JAVA_TOOL_OPTIONS` 双保险。
- 镜像内缺少 `ps`/`ss`/`netstat`，验证 JVM 参数改用 `cat /proc/1/cmdline | tr '\0' ' '`。
- 验证命令：`for i in 0 1 2; do kubectl exec zookeeper-$i -n hadoop1 -c zookeeper -- sh -c 'echo stat | nc -w 3 127.0.0.1 2181 | grep Mode'; done` 应见 1 leader + 2 follower。
- 注意：`zkServer.sh status` 报 "not running" 是**假阴性**（localhost→IPv6::1 而 ZK 监听 IPv4），用 `nc 127.0.0.1 2181` 直连才准。
- 真因：init 容器 `securityContext.runAsUser:0`（root），但 hdfs 命令被 `su hadoop -c` 降级；bootstrapStandby 调 Active NN 的 `isUpgradeFinalized` RPC 要求 superuser，hadoop 非超级用户被拒。
- 修复（`namenode.yaml`）：去掉所有 `su hadoop -c`，hdfs 命令以 root 运行；chown 改用 `id -u`/`:id -g`（=0:0）；Standby bootstrap 用 `-force -nonInteractive` 幂等重同步；去掉掩盖失败的 `|| echo`。
- 验证：`rollingUpgrade query` 显示 "There is no rolling upgrade in progress"（Active 未卡升级，那条 "in Upgrade" 仅为 bootstrap 良性分支日志，无需整体重建）。
- 恢复步骤：`kubectl apply -f namenode.yaml` → `kubectl delete pod namenode-1 -n hadoop` → 盯 init 日志出现 `Bootstrap 完成，本地 ClusterID:`。

## 命名空间可移植性重构（15:xx）
- 用户要求：部署文件不写死 namespace，仅在文档默认/推荐 `hadoop`，方便部署到不同 ns。
- 做法（相对域名方案，零工具）：
  1. 删除 7 个 YAML 里所有 `metadata.namespace: hadoop`（共 22 处）。`namespace.yaml` 保留（定义 `name: hadoop`，用于创建默认 ns）。
  2. 把所有写死的 FQDN 后缀 `.hadoop.svc.cluster.local` 去掉（configmap 11处、namenode 7、datanode 2、nodemanager 1、zookeeper 1 的 ZOO_SERVERS）。如 `namenode-0.namenode.hadoop.svc.cluster.local:9000` → `namenode-0.namenode:9000`。
  3. deploy-guide.md：所有 `kubectl apply/delete -f` 加 `-n hadoop`；新增命名空间可移植性说明；配置对照表 FQDN 同步改为相对域名。
- 原理：Pod 的 DNS 搜索域 `ns.svc.cluster.local` 会在同 ns 内自动补全短名 → 同一套 YAML 丢进任意 ns 都能解析。
- 注意：namespace 是不可变字段，已运行在 `hadoop` 的集群 re-apply 到同 ns 没问题；要换 ns 必须新建 ns 后全新 apply（旧对象留在 hadoop）。
- 备选方案（未采用）：Kustomize namespace transformer（企业级多环境）、envsubst 模板、或用户原方案（只去 ns 字段但 FQDN 仍写死 → 换 ns 必崩，不完整）。

## namenode "Could not determine own NN ID" 崩溃（15:07，部署到 hadoop1）
- 现象：namenode-0 主 NN 容器反复 `Error exit 1` + `Restart Count` 累加 + `BackOff`。日志抛 `java.lang.IllegalStateException: Could not determine own NN ID in namespace 'mycluster'. Please configure dfs.ha.namenode.id`。
- 真因：Hadoop `HAUtil` 在没有显式 `dfs.ha.namenode.id` 时，拿**容器 hostname**（`namenode-0`）去匹配 hdfs-site 里配置的 rpc-address（`namenode-0.namenode:9000`，带 Service 域名后缀）→ 对不上 → 自动识别失败 → NN 直接退出。**这是 Hadoop HA 跑在 K8s 上的经典必踩点**（hostname≠rpc-address），与之前 `|| echo`/su hadoop 的坑无关。
- 修复（`namenode.yaml`）：从"只读 subPath 挂载 ConfigMap"改为"init 容器生成可写配置 + 按 ordinal 注入 NN ID，主/ZKFC 共用"：
  1. 新增共享 `emptyDir` 卷 `hadoop-conf`。
  2. init 容器：`cp -rL /opt/hadoop/etc/hadoop/. /hadoop-conf/` + 覆盖 ConfigMap 的 core/hdfs-site.xml → 按 `ordinal=0→nn1`/`≠0→nn2` 用 `sed` 注入 `<property><name>dfs.ha.namenode.id</name><value>nn1|nn2</value></property>` 到 hdfs-site.xml → `export HADOOP_CONF_DIR=/hadoop-conf`。
  3. 主 NN 与 ZKFC 容器改挂 `hadoop-conf` 到 `/opt/hadoop/etc/hadoop`（去掉原 subPath 挂载）。ConfigMap 卷改全量挂到 init 的 `/config-source`。
- 顺手修：`configmap.yaml` 的 `dfs.namenode.name.dir` 由 `/opt/hadoop/data/nn1,...` 改为 `file:///opt/hadoop/data/nn1,file:///opt/hadoop/data/nn2`，消除 "Path should be specified as a URI" WARN。
- 恢复：`kubectl apply -f namenode.yaml -n hadoop1` → 因改了 volume 定义，删 pod 触发重建 `kubectl delete pod namenode-0 namenode-1 -n hadoop1`（PVC 持久，ordinal=0 见 VERSION 跳过 format，直接 initializeSharedEdits；nn1 健康后 namenode-1 才会 OrderedReady 启动并 bootstrapStandby）。
- 验证：`kubectl logs namenode-0 -n hadoop1 -c namenode` 应见 `本节点 NN ID = nn1` 且不再抛 NN ID 异常；`kubectl get pods -n hadoop1` 见 namenode 2/2、datanode 脱离 Init。
- 关键教训：**Hadoop HA on K8s 必须显式 `dfs.ha.namenode.id`**（不能依赖 hostname 自动识别），这是不同于裸机/VM 部署的差异点；共享 ConfigMap 无法直接写死（两 pod 会冲突），必须在 init 里按 ordinal 注入。

## NN ID 注入失败二次排障（15:15，同一 hadoop1 部署）
- 现象：按上次方案（sed 注入）重建后，`kubectl logs namenode-0 -c namenode | grep NN ID` **仍然抛 `Could not determine own NN ID`**（07:14:14 新 pod 日志）。说明注入没生效，但 init 容器却 `Completed exit 0`——假成功。
- 真因：① init 的 `hdfs namenode -initializeSharedEdits` 后面有 `|| { echo "跳过" }` 掩码，NN ID 缺失导致它失败时**被静默吞掉**；而 `hdfs namenode -format` 不需要 NN ID 也能成功 → init 整体 exit 0。② 实际注入用的 `sed 's#</configuration>#...\n...#'` 在镜像 `sed` 里**没有把 `\n` 渲染成换行**（生成畸形/未注入 XML），所以 `/opt/hadoop/etc/hadoop/hdfs-site.xml` 始终没有 `dfs.ha.namenode.id` → 主容器启动即崩。
- 修复（`namenode.yaml`）：
  1. init 注入从 `sed` 改为 **`awk`**（所有镜像自带，按行 `print` 生成标准 XML，无 `\n` 歧义）；并在注入后 `grep -A1` 回显校验，打印 `本节点 NN ID = nn1` 或 `!! NN ID 未注入 !!`。
  2. **主容器启动命令兜底注入**：`exec hdfs namenode` 之前，按 `${HOSTNAME##*-}` 计算 NN_ID，若 hdfs-site.xml 仍无该 property 则用同一段 awk 注入。这样即使 init 注入失败，主进程启动前配置也一定有 NN ID。
  3. 关键：主容器挂 `hadoop-conf`(emptyDir) 到 `/opt/hadoop/etc/hadoop` 且以 root 运行，awk 可写回该文件（temp 与 target 同目录，避免跨设备 mv 问题）。
- 结论：**凡是在容器里往 XML 注入属性，优先 awk 而非 sed `\n`；且不要对 HA 初始化命令用 `|| echo` 掩码**（会制造假成功，与之前 bootstrap 掩码同源问题）。
- 恢复：`kubectl apply -f namenode.yaml -n hadoop1` → `kubectl delete pod namenode-0 namenode-1 -n hadoop1` → 验证 init 日志 `本节点 NN ID = nn1` + 主日志 `主容器 NN ID = nn1` 且不再抛 NN ID 异常。
- **✅ 15:25 已验证生效**：`kubectl get all -n hadoop1` 显示 namenode-0/1 均 `2/2 Running`，datanode 3/3、journalnode 3/3、zookeeper 3/3，所有 StatefulSet 达期望副本。`RESTARTS 3/2` 为修复前崩溃累计，当前实例稳定（latest restart 37s/19s 前）。NN ID 注入（awk + 主容器兜底）方案彻底解决 HA 启动崩溃。后续建议：① 去掉 `initializeSharedEdits` 的 `|| echo` 掩码（防 JN 未就绪时静默跳过）；② 集群健康后可再评估 namenode 改 `Parallel`。

## ZK 无法组成 quorum 根因 + 注入机制踩坑（15:50-16:00，hadoop1）
- 现象：`zkServer.sh status` 3 个 ZK 全 `not currently serving`；选举日志 `QuorumPeer[myid=1]/0:0:0:0:0:0:0:0:2181` 的 `::`（IPv6 通配）+ `Cannot open channel to 3 at election address zookeeper-2.zookeeper/10.233.97.230:3888 → Connection refused`。DNS 解析本身正常（peer 解析到 IPv4 10.x）。
- **统一根因**：容器 hostname 经 nsswitch `myhostname` 只解析到 IPv6 链路本地 `fe80::`（已用 `getent hosts $(hostname)` 证实 NN 侧只返回 `fe80::...`）。ZK 据此把选举端口 3888 绑到 peer 不可达的 IPv6 地址 → 3 节点永远选不出 leader → `not currently serving`。NN 侧 `getLocalHost()` 返回 `(unknown)` 同源。
- **关键踩坑——`JAVA_TOOL_OPTIONS` 不可观测且本轮未生效**：第一版改 `ZOO_JAVA_OPTS`（3.4.14 镜像 entrypoint 不读 → 无效）；第二版改 `JAVA_TOOL_OPTIONS`（JVM 启动器无条件注入，**但不会出现在 `/proc/1/cmdline`**，无法验证，实测 ZK 仍绑 `::`，说明未真正生效）。**结论：强制 JVM IPv4 不能用这两个变量，因不可观测 + 实测无效。**
- **正确做法——`JVMFLAGS`**：`zkServer.sh` 会把环境变量 `JVMFLAGS` **显式拼进 java 命令行**（`java $JVMFLAGS org.apache.zookeeper...`），**必然出现在 `/proc/1/cmdline`，可一键验证**。已改 `zookeeper.yaml`：主容器 env 加 `JVMFLAGS=-Djava.net.preferIPv4Stack=true`（保留 JAVA_TOOL_OPTIONS 作冗余兜底）。并**删除无效的 `init-hosts` init 容器**——K8s 每个容器的 `/etc/hosts` 由 kubelet 独立管理，init 写的不会传给主容器；且 `127.0.0.1 $(hostname)` 对 ZK 是反向操作（绑回环，peer 更连不上）。
- NN 侧（`namenode.yaml`）保持 `HADOOP_OPTS=-Djava.net.preferIPv4Stack=true`（Hadoop 侧 HADOOP_OPTS 应生效）；因反复踩坑，也补了 `JAVA_TOOL_OPTIONS` 兜底。NN 的 `/etc/hosts` 写法是等 ZK 健康后再验证（NN 不依赖 peer 连自己回环，影响小于 ZK）。
- **可观测验证脚本**（下次执行）：`kubectl exec zookeeper-0 -n hadoop1 -c zookeeper -- cat /proc/1/cmdline | tr '\0' ' '` 必须出现 `-Djava.net.preferIPv4Stack=true`（JVMFLAGS 必在 argv）；随后 `for i in 0 1 2; do echo stat | nc -w 3 127.0.0.1 2181 | grep Mode; done` 应见 `leader`+`follower`。
- **剩余风险**：若 `preferIPv4Stack` 已确认进 cmdline 但 ZK 仍 `not currently serving`，则不是网络绑定问题，而是**长崩溃循环在 ZK PVC 留下损坏的选举状态** → 清 ZK PVC 重建：`kubectl delete pvc -l app=zookeeper -n hadoop1` + `kubectl apply -f zookeeper.yaml`（PVC 自动重建，全新集群无业务数据风险）。

## 17:00 ZK 根因确认：quorumListenOnAllIPs=false → 跨节点 3888 选主 Connection refused
- 诊断铁证：`ruok` 三节点均 `imok`（ZK 进程在跑、2181 监听正常）；选举日志 `Cannot open channel to 2/3 at election address zookeeper-1/2.zookeeper/10.233.x:3888 → Connection refused`。DNS 解析正确（peer→Pod IPv4 10.233.x），IPv4 已强制（JVMFLAGS 在 cmdline 生效）。→ 不是 DNS/IPv6/数据脏。
- **真因**：默认 `quorumListenOnAllIPs=false`，ZK 3.4.x 选举监听(`QuorumCnxManager.Listener`)只绑到解析出的**单一地址**（非 0.0.0.0）。其它 Pod 用 Pod IP 拨号 3888 时被 refused → 永远选不出 leader。2181 能通是因为客户端端口绑 0.0.0.0，而 3888 选举端口绑特定地址（这正是"2181 通、3888 拒"的反差原因）。
- **修复（`zookeeper.yaml`）**：改用 `command` 直接写完整 `zoo.cfg` 并 `exec zkServer.sh start-foreground`，内含 `quorumListenOnAllIPs=true`（绑 0.0.0.0:3888，任意网卡可接入）。保留 `JVMFLAGS/JAVA_TOOL_OPTIONS=-Djava.net.preferIPv4Stack=true`。移除对 ZOO_* 自动生成的依赖。
- 这是 ZK 跑在 K8s/Docker 上的经典坑；`quorumListenOnAllIPs=true` 是标准修法。
- 验证：`kubectl apply -f zookeeper.yaml -n hadoop1` + `scale 0 → delete pvc -l app=zookeeper → scale 3` → `for i in 0 1 2; do echo stat | nc -w 3 127.0.0.1 2181 | grep Mode; done` 应见 1 leader + 2 follower。
